# netcoop-msg/1.0 protocol reference

_Generated by `python tools/build_protocol_doc.py` from `schemas/message.schema.json`, `netcoop/catalog.py`, `config/thresholds.json` and a real run of the `conflicting_wifi_vs_congestion` scenario._

## 1. Envelope

Every inter-agent message is a JSON object with exactly these fields. The message bus validates it against the JSON Schema before delivery; invalid messages are not delivered and produce an `ERROR` message naming the faulty field.

| Field | Type | Required | Meaning |
|---|---|---|---|
| `protocol` | const | yes | Always `netcoop-msg/1.0`. Protocol name and version. Older versions are upgraded by a registered adapter before validation. |
| `msg_id` | string | yes | Unique id of this message. |
| `incident_id` | string | yes | Correlation id: every message about one diagnosis carries the same incident id. |
| `type` | enum | yes | One of: `TASK`, `TELEMETRY`, `FINDING`, `QUERY`, `RESPONSE`, `ERROR`, `REPORT` |
| `sender` | string | yes | Agent name of the sender. |
| `recipient` | string | yes | Agent name of the recipient, or '*' for broadcast. |
| `in_reply_to` | string / null | no | msg_id this message answers (RESPONSE, ERROR). |
| `timestamp` | string | yes | ISO 8601 UTC time the message was created. |
| `payload` | object | yes |  |

## 2. Message types

| Type | Sender → recipient | Purpose | Payload |
|---|---|---|---|
| `TASK` | orchestrator → agent | start a step | `action`: normalize / analyze / correlate / report; optional `notes` |
| `TELEMETRY` | ingestion_agent → `*` | canonical telemetry for everyone | canonical dataset (section 5) |
| `FINDING` | specialist / external → correlation_agent; correlation_agent → reporting_agent | evidence and hypotheses | section 3 |
| `QUERY` | correlation_agent → specialist | targeted follow-up question | `question`, `args`, `reason` |
| `RESPONSE` | specialist → correlation_agent | answer to a QUERY (`in_reply_to` required) | `question`, `supports`, `refutes`, `evidence`, `detail` |
| `ERROR` | any agent or the bus | failure that did not stop the run | `code`, `message`, `details` |
| `REPORT` | reporting_agent → orchestrator | final result | `report` (JSON), `markdown` |

## 3. FINDING payload

**finding**

| Field | Type | Required | Meaning |
|---|---|---|---|
| `agent_role` | string | yes |  |
| `status` | enum | yes | One of: `anomalies_found`, `no_anomalies`, `insufficient_data` |
| `observations` | array of evidence | yes | All evidence the agent considers relevant (abnormal values). |
| `hypotheses` | array of hypothesis | yes |  |
| `checked_metrics` | array of string | yes | Metrics the agent had data for and evaluated. |
| `missing_metrics` | array of string | yes | Metrics the agent owns but received no data for. |
| `data_quality` | number | yes | Range 0–1. |
| `summary` | string | no |  |
| `context` | object | no | Extra structured context, e.g. fault domain from topology. |

**hypothesis**

| Field | Type | Required | Meaning |
|---|---|---|---|
| `cause` | string | yes | Fault id from config/fault_signatures.json, e.g. link_congestion. |
| `score` | number | yes | Agent's local support for this cause, 0-1. Range 0–1. |
| `affected_devices` | array of string | yes |  |
| `evidence` | array of evidence | yes |  |
| `rationale` | string | no |  |

**evidence**

| Field | Type | Required | Meaning |
|---|---|---|---|
| `metric` | string | yes | Canonical metric name, e.g. link_utilization_pct (see docs/PROTOCOL.md). |
| `value` | number / string / boolean | yes | Median of the samples received, in the canonical unit. |
| `worst` | number / null | no | Worst sample when several were received; a peak past the threshold is graded at 85% strength. |
| `unit` | string | yes | ms, %, count, dBm, dB, Mbps, degC, state, ratio |
| `device_id` | string / null | no |  |
| `threshold` | number / null | no | Threshold the value was compared with. |
| `interpretation` | string | yes |  |
| `severity` | enum | yes | One of: `normal`, `warning`, `critical` |
| `source` | string | no | Agent that produced this evidence. |

## 4. QUERY questions

| `question` | Answered by | `args` | Answer semantics |
|---|---|---|---|
| `correlate_metrics` | performance_agent | `device`, `x` (default `link_utilization_pct`), `y` (default `latency_ms`) | Pearson r between `y` on the device and `x` on the device or any device upstream (best match, ≥ 4 paired samples). r ≥ 0.6 supports `link_congestion` and refutes `path_latency`; r ≤ 0.3 the reverse; otherwise inconclusive. |
| `baseline_connectivity` | performance_agent | `cause` | Healthy loss/latency on all devices supports the service fault in `cause`; problems on ≥ 50 % of devices refute it. |
| `device_detail` | infrastructure_agent | `device` | Critical status + errors supports `hardware_failure` over `device_overload`; saturated CPU/memory with clean interfaces the reverse. |
| `error_trend` | infrastructure_agent | `device` | CRC / interface errors rising across ≥ 3 samples while the link is not saturated supports `interface_fault` and refutes `link_congestion`. |
| `scope_check` | connectivity_agent | `device`, `cause` | Healthy wired neighbours support `weak_wifi_signal`; degraded neighbours refute it. With `cause=upstream_device_outage`: at least half the devices below the silent device cut off supports the outage. |

`supports` and `refutes` are fault ids (or `null`). The correlation agent applies +0.10 to a supported fault and −0.15 to a refuted one.

## 5. Canonical metrics, units and thresholds

All values in FINDING evidence and in TELEMETRY are in these units. Thresholds come from `config/thresholds.json` (direction `low` means smaller is worse).

| Metric | Unit | Valid range | Warning | Critical | Owner | Meaning |
|---|---|---|---|---|---|---|
| `latency_ms` | ms | 0 – 600000 | ≥ 100 | ≥ 250 | performance | Round-trip latency |
| `jitter_ms` | ms | 0 – 600000 | ≥ 30 | ≥ 60 | performance | Latency variation |
| `packet_loss_pct` | % | 0 – 100 | ≥ 1 | ≥ 5 | performance | Share of packets lost |
| `throughput_mbps` | Mbps | 0 – 1e+07 | – | – | performance | Observed throughput |
| `bandwidth_mbps` | Mbps | 0 – 1e+07 | – | – | performance | Link capacity |
| `link_utilization_pct` | % | 0 – 100 | ≥ 80 | ≥ 90 | performance | Link utilisation |
| `cpu_utilization_pct` | % | 0 – 100 | ≥ 80 | ≥ 95 | infrastructure | Device CPU utilisation |
| `memory_utilization_pct` | % | 0 – 100 | ≥ 85 | ≥ 95 | infrastructure | Device memory utilisation |
| `queue_drops` | count | 0 – ∞ | ≥ 50 | ≥ 150 | infrastructure | Egress queue drops in the interval |
| `interface_errors` | count | 0 – ∞ | ≥ 10 | ≥ 100 | infrastructure | Interface input/output errors |
| `crc_errors` | count | 0 – ∞ | ≥ 5 | ≥ 50 | infrastructure | CRC / FCS errors |
| `link_flaps` | count | 0 – ∞ | ≥ 1 | ≥ 3 | infrastructure | Link up/down transitions |
| `temperature_c` | degC | -40 – 150 | ≥ 65 | ≥ 80 | infrastructure | Device temperature |
| `rssi_dbm` | dBm | -120 – 0 | ≤ -67 | ≤ -75 | connectivity | Wi-Fi received signal strength |
| `snr_db` | dB | -20 – 100 | ≤ 25 | ≤ 15 | connectivity | Wi-Fi signal-to-noise ratio |
| `retransmission_pct` | % | 0 – 100 | ≥ 10 | ≥ 20 | connectivity | Wi-Fi frame retransmission rate |
| `connected_clients` | count | 0 – ∞ | – | – | connectivity | Clients associated / attached |
| `dns_failure_pct` | % | 0 – 100 | ≥ 5 | ≥ 20 | connectivity | Share of failed DNS queries |
| `dns_response_ms` | ms | 0 – 600000 | ≥ 200 | ≥ 1000 | connectivity | DNS response time |
| `dhcp_failure_pct` | % | 0 – 100 | ≥ 5 | ≥ 20 | connectivity | Share of failed DHCP requests |
| `dhcp_pool_utilization_pct` | % | 0 – 100 | ≥ 90 | ≥ 98 | connectivity | DHCP address pool in use |

Pseudo-metrics used in evidence:

| Metric | Unit | Produced by | Meaning |
|---|---|---|---|
| `device_status` | state | infrastructure_agent | `healthy`, `degraded` (warning) or `down` (critical), normalised from any status word (OK, Warning, Critical, up, red, …) |
| `telemetry_missing` | bool | connectivity_agent | device is in the topology but sent nothing |
| `downstream_impact` | count | connectivity_agent | devices below a silent device that are down, heavily lossy or silent |
| `corr(x,y)` | ratio | performance_agent | Pearson correlation returned in a RESPONSE |

Severity grades: `normal` (strength 0), `warning` (0.6 at the threshold, rising to 0.9), `critical` (0.9, rising to 1.0).

## 6. Telemetry input formats

The ingestion agent accepts any of these (mixed freely) and reports every translation:

```json
{
  "timestamp": "2026-10-31T10:05:00Z",
  "device_id": "SW_CAMPUS_4",
  "metrics": {
    "cpu_utilization_pct": 99.9,
    "latency_ms": 926.5
  },
  "status": "Critical"
}
```

Batch with topology (`schema_version` 0.x or 1.x; newer versions parsed best effort):

```json
{
  "schema_version": "1.1",
  "incident_id": "INC-001",
  "topology": {
    "devices": [
      {
        "id": "CORE_01",
        "type": "core",
        "upstream": null
      },
      {
        "id": "AP_01",
        "type": "ap",
        "segment": "hostel_A",
        "upstream": "CORE_01",
        "medium": "wireless"
      }
    ]
  },
  "records": [
    {
      "device_id": "AP_01",
      "timestamp": "2026-10-31T10:05:00Z",
      "metrics": {
        "rssi_dbm": -79
      }
    }
  ],
  "services": {
    "dns": {
      "failure_rate": 0.4,
      "response_ms": 1800
    }
  },
  "external_findings": [
    "<netcoop-msg/1.0 or 0.9 FINDING>"
  ]
}
```

Also: flat records (`{"host": "AP-3", "ts": 1730000000, "rtt": "0.25 s"}`), NDJSON, CSV, `topology.nodes/edges` with undirected links (oriented by device tier), per-record or batch `units` maps, value-with-unit objects (`{"value": 12, "unit": "ms"}`), epoch seconds or milliseconds.

## 7. Legacy netcoop-msg/0.9 and the adapter

```json
{
  "version": "0.9",
  "from": "campus_nms_probe",
  "to": "correlation_agent",
  "kind": "finding",
  "sent_at": 1793440200,
  "data": {
    "issue": "Uplink congestion on hostel distribution",
    "conf": 0.7,
    "devices": [
      "HOSTEL_DIST_SW_01"
    ],
    "readings": {
      "ifUtil": "96%",
      "outDiscards": 280
    }
  }
}
```

The adapter maps `from/to/kind/sent_at/data` to the 1.0 envelope, converts `readings` with the same field and unit translator as telemetry, maps the free-text `issue` to a fault id by keywords, and wraps everything in a FINDING with `agent_role: external`. The upgraded message is then validated like any other and carries `context.protocol_note`.
